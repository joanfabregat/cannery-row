# System specification (draft v0.2)

## Scope and ownership

Cannery Row owns projects, users and project memberships, research tracks, durable hypothesis/attempt state, exclusive work claims, artifact ingestion, the test and evaluation job queue, the stock evaluator (`cannery evaluator`, an evaluator like any other), validation, audit history, comments, search, the REST API, the MCP server and the web app. Human/agent discussion that *creates* a hypothesis is out of scope; the framework only receives and manages the resulting record. An agent may run an experiment, but it cannot mark its own measurements authoritative or promote itself. Testers and evaluators are external services that pull work from Cannery Row; the API process never executes project or candidate code.

One installation hosts several projects. The core is project-neutral. Each project owns versioned configuration revisions stored in the database: hypothesis extension schema, metric catalog and slices, immutable control/baseline references, tester registrations, result extension schema, the evaluator registration, resource limits, and dashboard view definitions. Tracks, memberships and comments are live records managed in the app, not configuration revisions.

## Technology choices

- **One process.** A single Rust binary, `cannery`, runs an async API server (Axum on Tokio) that serves REST, MCP and the built web app, and runs periodic background tasks. The service is primarily validation, state management and integration. Testers and evaluators can use any language.
- **PostgreSQL as the system of record, accessed with raw SQL.** No ORM or query builder. SQLx executes hand-written SQL that is checked against the schema at compile time; rows map to typed structs. Migrations are numbered `.sql` files in `crates/core/migrations/`, compiled into the binary and applied in order by a small in-repository runner, one transaction per file, tracked in a `schema_migrations` table. Transactions, constraints and row-level locking support race-safe claims without another queue service. [PostgreSQL documents `SKIP LOCKED` for queue-like consumers](https://www.postgresql.org/docs/current/sql-select.html).
- **Background tasks run inside the API process.** Lease expiry for agents and testers, failure review cases for expired leases or missed deadlines, automatic test/evaluation reruns, and orphaned-upload reconciliation run as periodic tasks guarded by a PostgreSQL advisory lock, so several replicas can run and only one executes a sweep at a time. There is no separate worker process and no outbox: testers and evaluators pull their jobs, so Cannery Row makes no outbound delivery calls.
- **React web app in this repository.** Vite + TypeScript + React, with a typed API client generated from the service's OpenAPI document. The `cannery` binary embeds the built assets and serves them. The app covers the dashboard, hypothesis/track/attempt pages, draft and result review, failure review, comments and search.
- **Object storage behind a small provider-neutral port.** Two stores ship: the local filesystem (development, tests, single-host installs), where every byte streams through the API, and S3-compatible buckets (AWS S3, Cloudflare R2, Garage, MinIO), where clients send and fetch bytes directly through presigned URLs and the API only verifies and records them. A native GCS store may follow. GCS's S3 interoperability is partial and uses HMAC keys, whereas native client libraries support Application Default Credentials. [GCS interoperability](https://docs.cloud.google.com/storage/docs/interoperability), [GCS authentication](https://docs.cloud.google.com/storage/docs/authentication).
- **JSON Schema Draft 2020-12** validates the portable envelope and each project's snapshotted extensions. Hand-written schema files are the source of truth; internal typed models are not allowed to generate or redefine the public contract. A schema version is immutable once attempts use it. [JSON Schema specification](https://json-schema.org/draft/2020-12).

Do not let one storage provider's ETag, version ID, ACL, or signed-URL behavior leak into the contract. Store application-calculated SHA-256 and size. Treat provider generation/version as optional provenance. Objects are private; authorized downloads receive short-lived access or a streamed response. Persist stable object references, never expiring download URLs.

## Settings and configuration

**Installation settings** live in a TOML file and/or environment variables and change only on restart: database DSN, object-store backends and credentials, OIDC issuers and client settings, allowed login email domains, bootstrap administrator emails, public base URL, and secrets such as signing keys. Secrets come from environment variables or a secret file, never from the database.

**Everything dynamic lives in PostgreSQL**: projects, users, memberships, tracks, project configuration revisions, hypotheses and everything below them, comments and API tokens. A project configuration revision is immutable once created. It has two independently versioned parts: the **science revision** (schemas, metrics, baselines, tester registrations, evaluator registration, required artifact roles, limits, retry policy) and the **dashboard revision** (view definitions). Attempts pin only the science revision, so changing a chart never changes the rules an experiment runs under. How revisions are authored — files applied through the CLI/API, UI editors, or both — is an open question.

## Identities, roles and authentication

Humans log in to the web app and API with OIDC. Cannery Row is provider-neutral: it validates tokens from a configured OIDC issuer and maps the subject to a local user created on first login. Roles are stored in Cannery Row, per project, never read from identity-provider claims:

| Role | Scope | Can |
| --- | --- | --- |
| `viewer` | project | Read the dashboard, tracks, hypotheses, attempts, reports, verified and claimed metrics, verdicts, decisions and comments; search. No artifact access, except report assets. |
| `member` | project | Viewer rights, plus comment and download artifacts. |
| `researcher` | project | Member rights, plus create and edit drafts, manage tracks, and record every human decision: draft review, result review, failure review. |
| `admin` | installation | Create projects, grant and revoke memberships, create project configuration revisions, register service identities. Bootstrap admins come from installation settings. |

Machine identities are separate from human roles and are registered per project: `agent` (create drafts, claim hypotheses of `agent`-mode tracks, heartbeat, upload and submit under its current lease), `experimenter` (the identity of a Cannery Row runner of the experiment kind: claim hypotheses of `workflow`-mode tracks only, heartbeat, upload, submit, read its predecessor attempt's artifacts and report a run's failure under its current lease; it cannot create or revise drafts), `tester` and `evaluator` (claim jobs of their stage and publish only that stage's evidence). None of them can record a human decision.

MCP clients, the CLI and machine identities authenticate with **Cannery Row-issued bearer tokens**. A human creates a personal access token in the web app after OIDC login; it is scoped, expiring, revocable, and stored only as a hash. It works on a headless machine because no browser redirect is involved. Service tokens for agents, experimenters, testers and evaluators are issued by an admin. A claimed job additionally returns a **job lease token** that can only read that job's inputs and write under that job's output prefix. Federated workload tokens (for example Kubernetes service-account or Google service-account ID tokens) may later replace stored service tokens.

Every write records the **actor**, the accountable identity, and **via**, the channel (`ui`, `api`, `mcp`) plus the client or agent identity used. An autonomous agent using its own service token is the actor. A human working through an agent session with their personal token is the actor, and the agent appears in `via`. The server derives both from authentication; a payload cannot assert them.

## Tracks

A track is a line of research within a project, for example one architectural approach competing against another. Every hypothesis belongs to exactly one track, and tracks are a first-class dimension of the dashboard and search. A track has a project-local slug, a title, a Markdown description, and a lifecycle managed by researchers, each transition with a non-empty reason:

- `active`: accepts drafts; its queued hypotheses can be claimed.
- `paused`: frozen. Drafts may be created and reviewed, but its queued hypotheses cannot be claimed. Attempts already in progress finish and are reviewed normally.
- `archived`: read-only. It accepts no drafts. A track can be archived only when it has no draft, queued or active hypothesis. A researcher may reactivate it.

Allowed transitions are `active ↔ paused`, `active | paused → archived`, and `archived → active`.

A track also binds the **producer step** its candidates are tested with (see [Testers, steps and the runner](#testers-steps-and-the-runner)), falling back to the project default. Changing the binding is an audited researcher action with a reason, and the server rejects a producer whose output interface does not match what the project scorer consumes.

### Experiment modes

Every attempt goes through the same stages: the **experiment** produces a candidate and a claimed result sheet, the **test** re-runs and grades the submission, the **evaluation** applies the policy and gives a verdict, and a **human decision** promotes, rejects or calls it inconclusive. A track's `mode` says only who runs the experiment stage:

- `agent` (the default, and every track created before modes existed): an outside agent, such as a Codex or Claude Code session, claims a queued hypothesis through the REST API or MCP, does the work itself, uploads its artifacts and submits the claimed result sheet.
- `workflow`: a **Cannery Row runner** running the `experiment` job kind (a `[[kinds]]` entry of its configuration file) claims the hypothesis through the same claim endpoint, with an **experimenter** service token (a service account kind only runners hold) and `{"mode": "workflow"}`. It runs the track's **workflow**, an ordered list of registered experiment step manifests (`role: experiment`) the track names by name and revision, through a launcher, exactly as it runs a test job's steps. The hypothesis supplies the workflow's parameters: the `project_fields` of its approved revision, validated against the science revision's hypothesis schema when the draft was written, handed to every step in `/cr/job.json`. The runner then uploads the outputs and submits the last step's claimed sheet through the endpoints an agent uses.

From the submission on, the two modes are identical: the same freeze, test job, evaluation job and human review. Claims are separated by identity: only an experimenter claims in `workflow` mode, and an experimenter claims nothing else (its claims default to `workflow`); agents and researchers claim only in `agent` mode (`403` for `workflow`). So an outside agent can neither pass its work off as a registered workflow's nor choose how its own failures are classified. The attempt pins the workflow's step revisions and a deadline at claim, like the producer; the sweep fails a runner-driven attempt still running past its deadline (`deadline_exceeded`). Switching a track's mode or changing its workflow is an audited researcher action with a reason (`track.updated`, plus `track.mode_changed` when the mode changes); attempts already claimed keep what they pinned. A track is checked when it is created or changed, and its workflow again at each claim: every step is a registered experiment manifest that fits the science revision, never reads held-out labels, and the outputs cover what the track's producer and the science revision's `required_artifact_roles.attempt` need, with the last step writing the claimed sheet (see [contracts](contracts.md#workflow-tracks)). A claim **skips** a track whose workflow (or producer) no longer fits the current science revision, so the other tracks' hypotheses still flow; the track is not paused (pausing is a researcher's decision, with a reason), its hypotheses simply wait, and a claim that finds only such tracks answers `409 workflow_unavailable` naming them, which the runner logs, until a researcher fixes the track or the science revision.

## Data model and lifecycle

`project` owns memberships, tracks, configuration revisions and hypotheses; `track` groups hypotheses; `hypothesis` owns the proposed question and acceptance plan; `attempt` is one immutable experimental execution; `artifact` and `evidence_record` belong to an attempt; `test_run`, `evaluation_run`, `review_case`, and `decision` preserve the independent stages; `comment` attaches to a hypothesis or attempt. Terminal attempts and their evidence remain immutable, including failed, negative, and inconclusive work. Corrections are appended with authorship and supersession links rather than rewriting history.

Each hypothesis gets a sequential number per project, regardless of track, shown as `#123`; its attempts are `#123.1`, `#123.2`. A reference from another project is written `project-slug#123`. Hypotheses can carry typed relations to other hypotheses (`derived_from`, `supersedes`, `related_to`). `#123` mentions in Markdown fields and comments are auto-linked and indexed as backlinks. A rejected, inconclusive or failed idea is recycled by a human creating a new draft with a `derived_from` relation; nothing is recycled automatically.

Hypothesis states: `draft → queued → active → awaiting_human_review → promoted | rejected | inconclusive`, with `declined` possible during draft review, `failed` when a researcher closes a workflow failure, and `cancelled` before a final result. A researcher first approves the draft as worth trying, with a recorded reason, before it enters `queued`; a request for revision leaves it in `draft`. `active` is a projection from an attempt in progress. The evaluator's verdict is a gate, not the final scientific decision. A researcher reviews the result or failure and records a disposition and reason. `promoted` means a human accepted a candidate that passed the configured gates; it does not replace an immutable baseline or authorize deployment, new training, or resource allocation. Using it as a future control requires an explicit new science revision. `failed` records that the workflow could not produce a result; it is not a scientific rejection. The web app shows `declined`, `rejected`, `inconclusive`, `failed` and `cancelled` hypotheses as **archived**: hidden by the default filter, always reachable, and fully searchable. Archive is a view, not a separate state.

Attempt states: `claimed → running → submitted → validating → testing → evaluating → awaiting_human_review → promoted | rejected | inconclusive`, with `failed` and `cancelled` terminal paths. Failures are handled in three classes:

- **Test or evaluation infrastructure failure** (runner crash, timeout, missing or invalid output): the frozen submission is intact, so Cannery Row reruns the failed stage automatically, up to the science revision's `max_auto_retries` (default 1). Each rerun is a new `test_run` or `evaluation_run` with its own identity and retained logs. When retries are exhausted, the attempt is `failed` and a human `failure` review case opens.
- **Agent-side failure** (lease expiry, upload verification failure, invalid submission, a producer output that the API itself refused against its registered interface): the attempt is `failed` and a human `failure` review case opens immediately.
- **Experiment run failure**, in `workflow` mode only (see [experiment modes](#experiment-modes)). The failure class of a runner-driven attempt comes from the experimenter runner's report, and that report is trusted, as a tester's word is for test infrastructure: an outside agent cannot hold an experimenter token, so it cannot pick its own classification. Every failure the experimenter reports when it releases the attempt (a step that exited non-zero or was killed, a deadline, a setup, a runner error, an input it could not stage or verify, step code it could not fetch, an upload grant that expired, an output that broke its interface or validator, a claimed sheet that is not one JSON object), and every failure the sweep finds (an expired lease, a missed attempt deadline) is a failure of the run. The attempt is `failed`, the failure is recorded with `requeued: true` and its log references, and the hypothesis returns to `queued` automatically with no review case (`hypothesis.requeued` in the audit log); the next claim creates a new attempt linked to the failed one. This happens up to the pinned science revision's `max_auto_retries`, counted since the last failure that went to review; once they are exhausted, the failure opens a `failure` review case. The candidate is blamed at once only on evidence the API holds itself, exactly as in `agent` mode: an upload the API refused or could not verify, or a claimed sheet the API rejected at submission (`invalid_submission`). In `agent` mode every experiment failure stays agent-side, as before.

A researcher resolves a failure case with `retry` or `close_failed`, always with a reason. `retry` after an infrastructure failure schedules a new run of the failed stage on the same frozen submission. `retry` after an agent-side failure returns the hypothesis to `queued`; the next claim creates a new attempt linked to the failed one, which may reuse verified immutable inputs. `close_failed` keeps the failed attempt and moves the hypothesis to `failed`. Every transition has an actor, via, timestamp, reason, and prior/new state in the audit log. The attempt's hypothesis revision, science revision, baseline, tester identity, and evaluation policy are snapshotted at claim time, so later edits cannot silently change its rules. An evaluated attempt remains `awaiting_human_review` without a human decision; elapsed time is not tacit approval.

A hypothesis has at most one active attempt at a time in v1. Parallel attempts on one hypothesis are a recorded proposal ([#1](https://github.com/joanfabregat/cannery-row/issues/1)), not part of v1.

A research history kept outside Cannery Row is loaded with `cannery import` from a reviewed bundle ([import.md](import.md)). Its records keep their historical dates and carry `origin: imported` with a source reference; its measurements have the authorities `imported_artifact` and `imported_transcribed`, never `tester_verified`; and a finished imported run with no decision of its own is `unreviewed`, an attempt state only imports use. An imported draft or result awaiting review continues in the live workflow. The live API never creates imported records.

Claim is one PostgreSQL transaction that selects an eligible queued hypothesis in an `active` track, creates its attempt, increments its lease generation, and returns an opaque lease token. Heartbeats extend a bounded TTL. Mutations require the current token and generation; late agents are rejected. A background sweep expires dead leases. Unique constraints and idempotency keys protect draft creation, submission, job claims and job completion. Test and evaluation jobs are rows created in the same transaction as the state change that requires them. Never hold a DB transaction open for a GPU test.

## Submission, testing, and decision

1. A researcher or an agent submits a structured hypothesis with a track, project-specific fields, optionally a declared control, evaluation plan, budget, success and regression criteria. Cannery Row validates it and saves a `draft`. A researcher approves, requests revision, or declines it, always with a reason. Only approval queues it for an agent.
2. A Codex/Claude Code session claims a queued hypothesis through REST or MCP, heartbeats its lease, and uploads files through one-time upload grants that declare each file's size and SHA-256: streamed through the API, or, with an S3 store, sent straight to the bucket through presigned URLs (one PUT whose URL signs the declared SHA-256, or presigned parts of a multipart upload the API created), then finished by a request in which the API verifies the stored object; mismatching bytes are deleted ([the protocol](contracts.md#uploads-and-downloads)). It submits a standardized **claimed result sheet** that includes the full Markdown report, plus an artifact manifest. The sheet can contain agent-observed metrics but they are labeled unverified. The API verifies object presence, byte counts and SHA-256, then freezes the submission. Invalid or missing artifacts produce a recorded failure and human review case, not silent replacement.
3. The freeze creates an immutable test job containing the claimed sheet and artifact identities, source revision, registered tester identity/version, dataset/control identities, science revision, resource ceiling and deadline. A registered external tester **claims** the job with a lease, exactly like an agent claims a hypothesis, receives a job lease token, downloads its inputs through scoped grants, uploads outputs under a create-only prefix, and posts its evidence. The tester is responsible for safely sandboxing any candidate code it chooses to execute; Cannery Row never executes submitted code. Cannery Row still limits the tester's credentials, input/output access and deadline. A tester is either the track's producer step followed by the project's scorer step, executed by the Cannery Row runner, or a self-hosted service that calls the job API itself (see [Testers, steps and the runner](#testers-steps-and-the-runner)). Duplicate completion cannot double-publish a result.
4. The tester checks the claimed sheet against the supplied artifacts and emits the same versioned evidence envelope, now with authoritative measurements, discrepancies, and test outputs. Cannery Row validates its producer identity, metric types/units/slices, completeness, provenance, finite numeric values, artifact manifest, and contract version. Evaluation then applies the policy of the **evaluator** the pinned science revision registers, which claims evaluation jobs like a tester: Cannery Row applies no gates itself. The stock evaluator, `cannery evaluator`, applies declarative gates from its own versioned configuration; a project needing a richer policy runs its own. Every evaluator records a `pass`, `fail`, or `inconclusive` verdict, the result of each gate, a non-empty reason and, optionally, the comparisons behind them (each value with the reference it was compared against: a paper, a benchmark, a promoted attempt, a baseline), in the same evaluator envelope. The evaluator cannot make the final decision. Treating missing required evidence as never `pass` is the evaluator's responsibility (the stock evaluator reports such a gate `unknown`); Cannery Row enforces only that a `pass` verdict reports every gate as passed. Infrastructure failure follows the retry rules above.
5. A researcher sees the report, claimed and verified measurements, discrepancies, evaluator verdict and reason, gate results, and source artifacts, then records `promote`, `reject`, or `inconclusive` with a non-empty reason. Promotion requires an evaluator `pass`; a `fail` or `inconclusive` verdict cannot be overridden into promotion without a corrected science revision and a new evaluation. If a stage failed, a researcher instead records `retry` or `close_failed` with a reason. The server attaches the authenticated actor, via, timestamp, and evidence revision. Decisions and reasons are immutable; a correction is a new linked decision event with its own reason.
6. The web app shows hypotheses, tracks, attempts, events, reports, verified metrics, controls, evaluator verdicts and human decisions. It must clearly distinguish agent claims from verified measurements, evaluator judgments from human decisions, and pending review from final states. Failures and superseded records remain visible.

The API validates envelope structure; the project's science revision defines scientific meaning. A project's evaluation policy can require per-language gates, uncertainty, cost limits, and fresh confirmation. A lower loss alone is not a retrieval win. Passing those gates only makes an attempt eligible for human promotion. Interpreting missing or contradictory evidence as never a pass is the evaluator's job, as is the choice of gates; Cannery Row checks only that a `pass` verdict reports every gate as passed. Both evaluator and human must state their reasoning, including on negative or inconclusive outcomes.

## Testers, steps and the runner

Tracks of one project can need different code to exercise a candidate (for example a sparse model versus a dense+sparse hybrid) while their results must stay comparable. A tester is therefore split into two container steps run as a chain:

1. **Producer step, per track.** It runs the candidate and turns it into a project-defined intermediate output, for example ranked results per query. This is the only step that executes candidate code, inside its declared sandbox. It never receives held-out labels.
2. **Scorer step, per project.** It consumes the producer's intermediate output, the ground truth and the frozen claimed sheet, and emits the tester evidence envelope. It never executes candidate code. Because every track uses the same scorer, metrics, slices and uncertainty are computed identically across tracks.

An **interface** is a registered name and version (for example `ranked-run/v1`) with a JSON Schema or format identifier describing the intermediate output. The project's science revision holds the interfaces, the scorer manifest, datasets, controls, metric registry and evaluator registration, which together define comparability. Producer manifests are registered separately as immutable, individually revisioned records, so adding a producer for a new track does not mint a new science revision. At claim time the attempt pins the science revision, and the track's producer manifest revision; binding and claim both check that the producer's output interface is the scorer's input interface. A project that prefers a single producer that adapts to the payload binds every track to it.

The **Cannery Row runner** is part of this codebase (`cannery runner`): a separate process that claims test jobs with a tester service identity, runs the steps, moves inputs and outputs between object storage and the containers, verifies checksums, and completes or fails the job. It runs each step through a launcher: a local-process one for fixtures and development, a Docker one (one container per step, see [deployment](deploy.md#the-runner-on-a-container-optimized-os-vm)) and a Kubernetes one (one Pod per step, see [deployment](deploy.md#the-runner-on-kubernetes)). It holds the execution credentials; the API process holds none. Step manifests use the field names of Argo Workflows templates (`container`, `resources`, `activeDeadlineSeconds`, `inputs`/`outputs.artifacts` with `name` and `path`) plus a few Cannery Row extensions, so a later move to Argo Workflows or SkyPilot is a translation, not a redesign. The container contract is defined in [contracts](contracts.md#step-manifests-and-the-container-contract): containers read `/cr/job.json` and `/cr/inputs/<name>/`, write `/cr/outputs/<name>/`, get no network unless declared, hold no credentials and never call the API. A self-hosted tester that implements the job API directly remains possible for projects that do not use the runner.

The runner has an `experiment` job kind, configured as a `[[kinds]]` entry beside the `test` and `eval` kinds, for [`workflow` tracks](#experiment-modes). It holds an **experimenter** service token instead of a tester's, claims hypotheses with `{"mode": "workflow"}`, heartbeats the attempt's lease, and runs the workflow's experiment steps in order with the same container contract, launchers, code and setup handling, interface checks and validators as a test job. An experiment step is candidate code: it never receives held-out labels, and its `code.repo` must be in the science revision's candidate repositories. Its outputs become attempt artifacts (the role is the output's name), its logs `step_log`, `setup_log` and `validator_log`; the last step's `claimed_sheet` becomes the submitted claimed result sheet. A failure releases the attempt with an error code, the failing step and its logs; the API trusts that report (see the failure classes above).

## Reports, comments and search

Reports are stored in PostgreSQL, not as artifacts: the structured report fields and the full Markdown body are part of the claimed result sheet, and tester observations are part of the tester envelope. Viewers can read reports. Images embedded in a report are uploaded as artifacts with the `report_asset` role, which viewers may read; every other artifact role (raw results, datasets, weights, logs) requires `member` or above. Report size is capped by project configuration.

Members and researchers comment in Markdown on hypotheses and attempts. An author can edit their own comment; every edit is retained and visible as history. Comments are discussion, not part of the scientific record: they never change state, verdicts or decisions.

A **general search** covers tracks, hypotheses, attempts, reports, tester observations, evaluator reasons, decision reasons and comments, within the projects the caller can read. It combines full text with facets: project, track, hypothesis state, attempt state, evaluator verdict, human decision, actor, and time range. `#123` and `project#123` queries resolve directly. v1 uses PostgreSQL full-text search with the `simple` configuration plus `pg_trgm` trigram matching, which suits mixed French/English text; a dedicated search engine is only warranted by demonstrated need. Results are filtered by permission before ranking, and artifact contents are never indexed. Search is available in the web app, REST and MCP, so an agent can check for prior related work before drafting.

## Interfaces

REST is the canonical interface; MCP is a thin, authenticated adapter over the same application methods and permission checks, with no separate persistence or business rules, served over Streamable HTTP by the same process. Initial operations: create/update draft; review draft; list/get/filter/search tracks, hypotheses and attempts; manage tracks; claim/heartbeat/release; create scoped upload; submit claimed sheet/manifest; claim/heartbeat/complete/fail test and evaluation jobs; list events/evidence/metrics/verdicts/review cases; record a human result or failure decision; comment; retrieve a permitted artifact; manage personal access tokens. Human-decision operations require the `researcher` role and a non-empty reason; agent, experimenter, tester and evaluator identities cannot call them. Status transitions require expected version or lease generation. List APIs paginate and filter by project, track, state, time, metric and dimension; bulk metrics queries serve charts without a query per point.

The dashboard revision defines named views, metric axes/units, slice facets, baseline overlays and default filters, referencing only registered metrics and dimensions, with tracks usable as a grouping dimension. Without dashboard views, the app derives defaults from the metric registry: a table, per-metric timelines and per-dimension breakdowns. Grafana may later consume exported metrics, but is not the primary research UI: reports, provenance, attempt history and decisions need first-class pages.

## Web app design

The audience includes enterprise clients and non-technical viewers, so the app must look calm, modern and trustworthy, while staying compatible with the playful vintage cannery logo. The logo carries the personality; the interface stays plain.

- **Look.** Clean, generous whitespace, one sans-serif typeface (Inter or similar) for everything, no decorative fonts in the UI. Colors come from the logo, used sparingly: deep navy ink for text and navigation, cream as a warm neutral surface, silver-greys for borders and secondary text, and the label's coral red only for the primary action and key highlights. Status colors are semantic and never rely on color alone: every state chip also has a word and an icon. Light theme by default, dark theme supported. Accessible contrast (WCAG AA) and full keyboard navigation.
- **Components.** React with an accessible headless component base (Radix primitives through shadcn/ui, styled with Tailwind), TanStack Query and Table, and one chart library. No custom widget where a standard one exists.
- **Navigation.** One left sidebar with at most six entries, labeled in plain words: **Home** (what needs my attention: drafts and results awaiting review, failures, running work), **Tracks**, **Hypotheses**, **Results** (dashboard views), **Search**, and **Settings** (tokens; project and membership admin only for admins). A project switcher sits at the top of the sidebar and disappears when the user belongs to one project. Search is also a global bar reachable from every page. Actions a role cannot perform are hidden, not disabled.
- **Plain language.** Internal state names never appear raw: `awaiting_human_review` is shown as "Needs review", `agent_claim` as "Reported by agent", `tester_verified` as "Verified". Every hypothesis page answers first, in one sentence at the top, "what was tried, what happened, what was decided and why", before any metrics, evidence or lineage, which stay one click away.
- **Depth on demand.** Lists and pages open on the summary; technical detail (revisions, hashes, manifests, logs, raw envelopes) lives in collapsible sections or a "Details" tab, so a viewer never has to scroll past it and a researcher never loses it.
- **Decisions.** Review flows are one screen: the evidence summary, the evaluator verdict and gate results, the action buttons, and a required reason field. The button stays disabled until a reason is typed, and the confirmation states what will happen in plain words.

## Trust, security and recovery

v1 requires one researcher decision with a reason, not votes or multi-reviewer quorum; retain an append-only decision model so those can be added later. All APIs, pages, reports and artifacts require an authenticated identity with a role on the project; public result pages are outside v1. Treat submitted code, reports, comments and artifact names as untrusted; the web app renders Markdown sanitized. The framework must allowlist object prefixes and media types, cap upload and report sizes, and never pass its DB or broad bucket credentials to a tester. The tester owns safe execution of candidate code when its evaluation requires it and must declare its sandbox and capability policy; the framework gives it only scoped inputs/outputs and a deadline. Tester and evaluator evidence requires their service identities; an agent cannot submit it.

PostgreSQL and object storage require backups and restore tests. The DB stores verified object inventory and hashes, but an object is not durable merely because an upload request succeeded. Reconcile orphaned uploads and missing objects; publish an attempt only after verifying required objects. Preserve source/config/tester identities and all terminal records. Capture cost and duration for queue wait, agent work, test runtime, evaluation and total wall time. Use UTC instants in storage and localize only in the UI.

## Generic versus project-specific boundary

Generic: projects, users, roles, tracks, lifecycle, leases, audit, API/MCP, web app, schema registry, object references, upload verification, job queue and failure review, the runner and its container contract, evidence ingestion, metric storage/query, evaluator comparisons, the stock evaluator, comments, search, dashboard rendering. Project-specific: hypothesis extension fields, dataset and control identities, interfaces, the scorer step, per-track producer steps and their sandbox, evaluator and its configuration (gates, baseline values), metric registry, required slices, resource budgets, dashboard views. The core may know what a metric, a track and a baseline are; it must not know what nDCG, a GPU, or a particular project's dataset means.
