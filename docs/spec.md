# System specification (draft v0.2)

## Scope and ownership

Cannery Row owns projects, users and project memberships, research tracks, durable unit/attempt state, exclusive work claims, artifact ingestion, the verify job queue, the stock policy (`cannery evaluator`, a policy like any other), validation, audit history, comments, search, the REST API, the MCP server and the web app. Human/agent discussion that *creates* a unit is out of scope; the framework only receives and manages the resulting record. An agent may run an experiment, but it cannot verify its own run, mark its own measurements authoritative or promote itself. Verifiers are external: a runner holding a verifier service account, or an agent or researcher who did not run the attempt, pulls verify jobs from Cannery Row; the API process never executes project or candidate code.

One installation hosts several projects. The core is project-neutral. Each project owns versioned configuration revisions stored in the database: unit extension schema, metric catalog and slices, immutable control/baseline references, result extension schema, who verifies a run (the verifier registration and its policy revision), resource limits, and dashboard view definitions. Tracks, memberships and comments are live records managed in the app, not configuration revisions.

## Technology choices

- **One process.** A single Rust binary, `cannery`, runs an async API server (Axum on Tokio) that serves REST, MCP and the built web app, and runs periodic background tasks. The service is primarily validation, state management and integration. Verifiers and their policies can use any language.
- **PostgreSQL as the system of record, accessed with raw SQL.** No ORM or query builder. SQLx executes hand-written SQL that is checked against the schema at compile time; rows map to typed structs. Migrations are numbered `.sql` files in `crates/core/migrations/`, compiled into the binary and applied in order by a small in-repository runner, one transaction per file, tracked in a `schema_migrations` table. Transactions, constraints and row-level locking support race-safe claims without another queue service. [PostgreSQL documents `SKIP LOCKED` for queue-like consumers](https://www.postgresql.org/docs/current/sql-select.html).
- **Background tasks run inside the API process.** Lease expiry for agents and verifiers, failure review cases for expired leases or missed deadlines, automatic verify reruns, and orphaned-upload reconciliation run as periodic tasks guarded by a PostgreSQL advisory lock, so several replicas can run and only one executes a sweep at a time. There is no separate worker process and no outbox: verifiers pull their jobs, so Cannery Row makes no outbound delivery calls.
- **React web app in this repository.** Vite + TypeScript + React, with a typed API client generated from the service's OpenAPI document. The `cannery` binary embeds the built assets and serves them. The app covers the dashboard, unit/track/attempt pages, plan and result review, failure review, comments and search.
- **Object storage behind a small provider-neutral port.** Two stores ship: the local filesystem (development, tests, single-host installs), where every byte streams through the API, and S3-compatible buckets (AWS S3, Cloudflare R2, Garage, MinIO), where clients send and fetch bytes directly through presigned URLs and the API only verifies and records them. A native GCS store may follow. GCS's S3 interoperability is partial and uses HMAC keys, whereas native client libraries support Application Default Credentials. [GCS interoperability](https://docs.cloud.google.com/storage/docs/interoperability), [GCS authentication](https://docs.cloud.google.com/storage/docs/authentication).
- **JSON Schema Draft 2020-12** validates the portable envelope and each project's snapshotted extensions. Hand-written schema files are the source of truth; internal typed models are not allowed to generate or redefine the public contract. A schema version is immutable once attempts use it. [JSON Schema specification](https://json-schema.org/draft/2020-12).

Do not let one storage provider's ETag, version ID, ACL, or signed-URL behavior leak into the contract. Store application-calculated SHA-256 and size. Treat provider generation/version as optional provenance. Objects are private; authorized downloads receive short-lived access or a streamed response. Persist stable object references, never expiring download URLs.

## Settings and configuration

**Installation settings** live in a TOML file and/or environment variables and change only on restart: database DSN, object-store backends and credentials, OIDC issuers and client settings, allowed login email domains, bootstrap administrator emails, public base URL, and secrets such as signing keys. Secrets come from environment variables or a secret file, never from the database.

**Everything dynamic lives in PostgreSQL**: projects, users, memberships, tracks, project configuration revisions, units and everything below them, comments and API tokens. A project configuration revision is immutable once created. It has two independently versioned parts: the **science revision** (schemas, metrics, baselines, who verifies a run, required artifact roles, limits, retry policy) and the **dashboard revision** (view definitions). Attempts pin only the science revision, so changing a chart never changes the rules an experiment runs under. How revisions are authored — files applied through the CLI/API, UI editors, or both — is an open question.

## Identities, roles and authentication

Humans log in to the web app and API with OIDC. Cannery Row is provider-neutral: it validates tokens from a configured OIDC issuer and maps the subject to a local user created on first login. Roles are stored in Cannery Row, per project, never read from identity-provider claims:

| Role | Scope | Can |
| --- | --- | --- |
| `viewer` | project | Read the dashboard, tracks, units, attempts, reports, verified and claimed metrics, verdicts, decisions and comments; search. No artifact access, except report assets. |
| `member` | project | Viewer rights, plus comment and download artifacts. |
| `researcher` | project | Member rights, plus write plans, manage tracks, and record every human decision: plan review, the decision on a unit, failure review; write a unit up or skip its write-up. |
| `admin` | installation | Create projects, grant and revoke memberships, create project configuration revisions, register service identities. Bootstrap admins come from installation settings. |

Machine identities are separate from human roles and are registered per project: `agent` (claim units of `agent`-mode tracks, heartbeat, upload and submit under its current lease), `experimenter` (the identity of a Cannery Row runner of the experiment kind: claim units of `workflow`-mode tracks only, heartbeat, upload, submit, read its predecessor attempt's artifacts and report a run's failure under its current lease; it cannot write plans), `verifier` (the identity of a Cannery Row runner of the verify kind: claim verify jobs registered to its name under its policy revision and publish their verification reports), `decider` (the identity of a Cannery Row runner of the decide kind: claim decide jobs registered to its name under the revision of its decider step and record the decision documents that step writes). An `agent` service account may also claim verify jobs whose performer is `agent`, never for an attempt it claimed itself. Any of them, like members and researchers, may raise a concern about a track's plan. None of them can record a human decision; a decider's decision is an automatic one, recorded with the decider and its step revision as the actor.

MCP clients, the CLI and machine identities authenticate with **Cannery Row-issued bearer tokens**. A human creates a personal access token in the web app after OIDC login; it is scoped, expiring, revocable, and stored only as a hash. It works on a headless machine because no browser redirect is involved. Service tokens for agents, experimenters, verifiers and deciders are issued by an admin. A claimed job additionally returns a **job lease token** that can only read that job's inputs and write under that job's output prefix. Federated workload tokens (for example Kubernetes service-account or Google service-account ID tokens) may later replace stored service tokens.

Every write records the **actor**, the accountable identity, and **via**, the channel (`ui`, `api`, `mcp`) plus the client or agent identity used. An autonomous agent using its own service token is the actor. A human working through an agent session with their personal token is the actor, and the agent appears in `via`. The server derives both from authentication; a payload cannot assert them.

## Tracks

A track is a line of research within a project, for example one architectural approach competing against another. Every unit belongs to exactly one track, and tracks are a first-class dimension of the dashboard and search. A project is created with at least one track, in the same request, so a project never exists without a line of research to plan; researchers add more later. A track has a project-local slug, a title, a Markdown description, and a lifecycle managed by researchers, each transition with a non-empty reason:

- `planning`: a new track starts here. Its plan is written and reviewed (see [Track plans](#track-plans)), but nothing in it can be claimed. Approving its first plan makes it `active`.
- `active`: accepts plans; its queued units can be claimed.
- `paused`: frozen. Drafts and plans may be created and reviewed, but its queued units cannot be claimed. Attempts already in progress finish and are reviewed normally.
- `archived`: read-only. It accepts no plans. A track can be archived only when it has no queued, active, documenting or deciding unit. A researcher may reactivate it.

Allowed transitions are `planning | active → paused`, `paused → active`, `planning | active | paused → archived`, and `archived → active`. A track resumed or reactivated before any plan was approved and with no unit goes back to `planning`. Tracks that existed before plans and already hold units were migrated to `active`.

A track also binds the **producer step** its candidates are verified with (see [Verifiers, steps and the runner](#verifiers-steps-and-the-runner)), falling back to the project default. Changing the binding is an audited researcher action with a reason, and the server rejects a producer whose output interface does not match what the project scorer consumes.

### Experiment modes

Every attempt goes through the same stages: the **experiment** produces a candidate and a run document, the **verify** job checks the submission and gives a verdict under the registered policy, and a **human decision** promotes, rejects or calls it inconclusive. A track's `mode` says only who runs the experiment stage:

- `agent` (the default, and every track created before modes existed): an outside agent, such as a Codex or Claude Code session, claims a queued unit through the REST API or MCP, does the work itself, uploads its artifacts and submits the run document.
- `workflow`: a **Cannery Row runner** running the `experiment` job kind (a `[[kinds]]` entry of its configuration file) claims the unit through the same claim endpoint, with an **experimenter** service token (a service account kind only runners hold) and `{"mode": "workflow"}`. It runs the track's **workflow**, an ordered list of registered experiment step manifests (`role: experiment`) the track names by name and revision, through a launcher, exactly as it runs a verify job's steps. The unit supplies the workflow's parameters: the `project_fields` of its approved revision, validated against the science revision's unit schema when its plan was checked, handed to every step in `/cr/job.json`. The runner then uploads the outputs and submits the last step's claimed sheet through the endpoints an agent uses.

From the submission on, the two modes are identical: the same freeze, verify job and human review. Claims are separated by identity: only an experimenter claims in `workflow` mode, and an experimenter claims nothing else (its claims default to `workflow`); agents and researchers claim only in `agent` mode (`403` for `workflow`). So an outside agent can neither pass its work off as a registered workflow's nor choose how its own failures are classified. The attempt pins the workflow's step revisions and a deadline at claim, like the producer; the sweep fails a runner-driven attempt still running past its deadline (`deadline_exceeded`). Switching a track's mode or changing its workflow is an audited researcher action with a reason (`track.updated`, plus `track.mode_changed` when the mode changes); attempts already claimed keep what they pinned. A track is checked when it is created or changed, and its workflow again at each claim: every step is a registered experiment manifest that fits the science revision, never reads held-out labels, and the outputs cover what the track's producer and the science revision's `required_artifact_roles.attempt` need, with the last step writing the claimed sheet (see [contracts](contracts.md#workflow-tracks)). A claim **skips** a track whose workflow (or producer) no longer fits the current science revision, so the other tracks' units still flow; the track is not paused (pausing is a researcher's decision, with a reason), its units simply wait, and a claim that finds only such tracks answers `409 workflow_unavailable` naming them, which the runner logs, until a researcher fixes the track or the science revision.

## The brief

A project has one **brief**: the context everyone working on the project needs, written once instead of repeated in every unit. It is a Markdown document with YAML front matter, like a phase output: the front matter holds a `title` and a one-paragraph `goal` and is checked against the published `brief` schema (see [contracts](contracts.md#the-brief)); the body holds the domain, the constraints, the resources and the conventions.

Only researchers write the brief, through the web app, REST, MCP or a personal token; an agent writing for a researcher is recorded in `via`, and a service account cannot write one. Every save is a new immutable revision, numbered from 1, with its SHA-256, author and via; a save names the revision it replaces, so a concurrent edit is refused rather than lost. Everyone who can read the project reads the brief and its history.

Every claim response, an agent's, an experimenter's or a verifier's, names the brief revision the work runs under, with its SHA-256 and where to read it. The attempt pins the current revision at claim, like its science revision, and its verify jobs hand out that same revision, so a later edit never changes the context of work already started. A project may have no brief yet; its claims then name none.

## Track plans

A track's **plan** says how the track tests its idea and which **units** of work it runs. A plan is not a parsed document: it is a draft built through tools, the same REST routes and MCP tools for people and agents, and each track has one chain of plan revisions. A revision holds the **approach** (Markdown: the idea, the edge cases and risks, how the units fit together) and one entry per unit: a key unique in the track, the unit fields (title, question, intervention, optional control, the acceptance plan, optional parameters, relations), the **context** items its performer should read first (another unit, an attempt's write-up, an artifact, each with an optional note) and the unit's own Markdown **brief**.

A researcher, or an agent working for one (recorded in `via`), starts a revision from the approved one (or from the last revision sent back), sets the approach, adds, updates and drops units, and gives an **alignment** for every unit already done or in flight: `keep`, `obsolete` or `redo`, with a reason. `check_plan` lists what blocks a submission: no project brief (the first approval in a project needs one), no approach, missing alignment, unknown unit keys, units no longer queued and limits exceeded. Submitting opens a `plan` review case; a researcher approves, sends back or declines it, always with a reason. Service accounts cannot author or review plans (`403`).

Approval runs in one transaction: each new unit is queued with revision 1, each changed queued unit gets a new revision, queued units the plan drops are cancelled, and the alignment applies: `obsolete` marks the unit obsolete and cancels an attempt in flight (the attempt and its evidence are kept), and `redo` is `obsolete` plus a new unit `derived_from` the old one. The first approval moves a `planning` track to `active`. Unit revisions written by a plan carry the unit's brief. Plans are the only way units are created.

A claim pins the approved plan revision of its track, like the brief. Its response names the attempt's **context bundle**, assembled on demand from the pinned revisions and never stored: the project brief, the plan's approach, the unit's fields and brief, a one-line index of the track's other units, and a summary line with a reference for each context item and for each output of the units it derives from. The bundle states its own byte size; a compact form keeps the goal, the unit and the index under 16 KiB.

Anyone working on a track can say the plan is wrong. A **concern** is raised through REST or MCP (`raise_concern`) by a member, a researcher or any of the project's service accounts, with the actor and `via` recorded like every write: Markdown whose YAML front matter (the published `concern` schema) holds its `kind` (`wrong_assumption`, `better_idea`, `blocker` or `other`) and, when it comes from one, the `unit` and `attempt` of the track, and whose non-empty body (at most 16 KiB) is the argument. While a concern is open, no new unit of its track can be claimed (`409 concern_open`); work already claimed continues, and a runner of the experiment kind waits as if nothing were queued. A concern closes in one of two ways: a plan revision answers it, saying how in its `answers` (`answer_concern`; `check_plan` reports every open concern the draft has not answered, and approval closes the answered ones), or a researcher dismisses it with a reason. A step run by `cannery runner` raises one by writing `/cr/outputs/concern/concern.md`, which the runner submits with its service token, naming the step's unit and attempt when the document names none; a concern never changes the step's result.

Each project sets **limits**, refused at the write call with the location, the size and the limit: the brief (64 KiB by default), the approach (64 KiB), a unit brief (32 KiB) and the number of context items per unit (64). The bundle's index lines (about 100 bytes) and summary lines (about 300 bytes) are truncated rather than refused.

## Data model and lifecycle

`project` owns memberships, tracks, its brief, configuration revisions and units; `track` groups units; `unit` owns the proposed question and acceptance plan; `attempt` is one immutable experimental execution; `artifact` and `phase_output` belong to an attempt; `job` (each run of the verify phase), `review_case`, and `decision` preserve the independent stages; `comment` attaches to a unit or attempt. Terminal attempts and their evidence remain immutable, including failed, negative, and inconclusive work. Corrections are appended with authorship and supersession links rather than rewriting history.

What each phase of an attempt produces is stored as a phase output: a document with YAML front matter (the machine-readable part, checked against the phase's published schema, see [contracts](contracts.md#phase-documents)) and a Markdown body (the narrative). The run phase stores its claims as front matter and its run notes as the body; the verification phase stores the verification report, its verdict, gates, verified measurements and provenance as front matter and the verifier's observations as an optional body; the report of an imported attempt is an imported write-up, whose front matter holds its kind, author and date and whose body is the report itself.

Each unit gets a sequential number per project, regardless of track, shown as `#123`; its attempts are `#123.1`, `#123.2`. A reference from another project is written `project-slug#123`. Units can carry typed relations to other units (`derived_from`, `supersedes`, `related_to`). `#123` mentions in Markdown fields and comments are auto-linked and indexed as backlinks. A rejected, inconclusive or failed idea is recycled by a new unit in a plan, with a `derived_from` relation; nothing is recycled automatically.

Unit states: `queued → active → documenting → deciding → promoted | rejected | inconclusive | failed`, and `cancelled` before a final result. `documenting` waits for the write-up, `deciding` for the decision; `failed` is the decision on a unit a researcher stopped after a workflow failure. A unit is created only by the approval of its track's plan, which lists it, and enters `queued` then: the plan review is where a researcher judges the idea worth trying, with a recorded reason. `active` is a projection from an attempt in progress. The verifier's verdict is a gate, not the final scientific decision. A researcher decides each written-up unit, or resolves a failure, and records a disposition and reason. `promoted` means a human accepted a candidate that passed the configured gates; it does not replace an immutable baseline or authorize deployment, new training, or resource allocation. Using it as a future control requires an explicit new science revision. `failed` records that the workflow could not produce a result; it is not a scientific rejection. The web app shows `rejected`, `inconclusive`, `failed` and `cancelled` units as **archived**: hidden by the default filter, always reachable, and fully searchable. Archive is a view, not a separate state.

Attempt states: `claimed → running → verifying → verified`, with `failed` and `cancelled` terminal paths. An attempt ends at `verified`, whatever the verdict: the write-up and the decision belong to the unit. Failures are handled in three classes:

- **Verify infrastructure failure** (runner crash, timeout, a step that failed, missing or invalid output from a runner, a verifier whose lease expired): the frozen submission is intact, so Cannery Row reruns the verify job automatically, up to the science revision's `max_auto_retries` (default 1). Each rerun is a new run of the job with its own identity and retained logs, and it resumes from the failed step, reusing the verified outputs of the steps before it. When retries are exhausted, the attempt is `failed` and a human `failure` review case opens.
- **Agent-side failure** (lease expiry, upload verification failure, invalid submission, a producer output that the API itself refused against its registered interface): the attempt is `failed` and a human `failure` review case opens immediately.
- **Experiment run failure**, in `workflow` mode only (see [experiment modes](#experiment-modes)). The failure class of a runner-driven attempt comes from the experimenter runner's report, and that report is trusted, as a verifier's word is for verify infrastructure: an outside agent cannot hold an experimenter token, so it cannot pick its own classification. Every failure the experimenter reports when it releases the attempt (a step that exited non-zero or was killed, a deadline, a setup, a runner error, an input it could not stage or verify, step code it could not fetch, an upload grant that expired, an output that broke its interface or validator, a claimed sheet that is not one JSON object), and every failure the sweep finds (an expired lease, a missed attempt deadline) is a failure of the run. The attempt is `failed`, the failure is recorded with `requeued: true` and its log references, and the unit returns to `queued` automatically with no review case (`unit.requeued` in the audit log); the next claim creates a new attempt linked to the failed one. This happens up to the pinned science revision's `max_auto_retries`, counted since the last failure that went to review; once they are exhausted, the failure opens a `failure` review case. The candidate is blamed at once only on evidence the API holds itself, exactly as in `agent` mode: an upload the API refused or could not verify, or a claimed sheet the API rejected at submission (`invalid_submission`). In `agent` mode every experiment failure stays agent-side, as before.

A researcher resolves a failure case with `retry` or `stop`, always with a reason. `retry` after an infrastructure failure schedules a fresh verify job on the same frozen submission. `retry` after an agent-side failure returns the unit to `queued`; the next claim creates a new attempt linked to the failed one, which may reuse verified immutable inputs. `stop` keeps the failed attempt and sends the unit to `documenting`: it is written up, then decided `failed`. Every transition has an actor, via, timestamp, reason, and prior/new state in the audit log. The attempt's unit revision, science revision, brief revision, baseline, verifier identity, and policy revision are snapshotted at claim time, so later edits cannot silently change its rules. A unit waits in `documenting` and `deciding` until someone acts: nothing skips a write-up or takes a decision automatically, and elapsed time is not tacit approval.

A unit has at most one active attempt at a time in v1. Parallel attempts on one unit are a recorded proposal ([#1](https://github.com/joanfabregat/cannery-row/issues/1)), not part of v1.

A research history kept outside Cannery Row is loaded with `cannery import` from a reviewed bundle ([import.md](import.md)). Its records keep their historical dates and carry `origin: imported` with a source reference; its measurements have the authorities `imported_artifact` and `imported_transcribed`, never `tester_verified`; and a finished imported run with no decision of its own is `unreviewed`, an attempt state only imports use. An imported result awaiting review continues in the live workflow: it is written up, then decided. The live API never creates imported records.

Claim is one PostgreSQL transaction that selects an eligible queued unit in an `active` track, creates its attempt, increments its lease generation, and returns an opaque lease token. Heartbeats extend a bounded TTL. Mutations require the current token and generation; late agents are rejected. A background sweep expires dead leases. Unique constraints and idempotency keys protect plan writes, submission, job claims and job completion. A verify job is a row created in the same transaction as the state change that requires it. Never hold a DB transaction open for a GPU run.

## Submission, verification, and decision

1. A researcher, or an agent working with one, writes a track's plan: its approach and its units, each with its acceptance, project-specific `parameters` and context. Cannery Row validates every unit and the plan as a whole. A researcher approves, sends back or declines the plan, always with a reason. Only approval creates the plan's units and queues them for an agent.
2. A Codex/Claude Code session claims a queued unit through REST or MCP, heartbeats its lease, and uploads files through one-time upload grants that declare each file's size and SHA-256: streamed through the API, or, with an S3 store, sent straight to the bucket through presigned URLs (one PUT whose URL signs the declared SHA-256, or presigned parts of a multipart upload the API created), then finished by a request in which the API verifies the stored object; mismatching bytes are deleted ([the protocol](contracts.md#uploads-and-downloads)). It records an artifact manifest, then submits its **run document**: Markdown whose YAML front matter holds its claims, provenance, artifact roles and the manifest reference, and whose body holds optional run notes. Its claimed metrics are labeled unverified. A run that failed submits no document: it releases the attempt with a failure report. The API verifies object presence, byte counts and SHA-256, then freezes the submission. Invalid or missing artifacts produce a recorded failure and human review case, not silent replacement.
3. The freeze moves the attempt to `verifying` and creates one immutable **verify job** containing the run document's front matter and artifact identities, source revision, dataset/control identities, science revision, the producer and scorer steps, resource ceiling and deadline. The pinned science revision's `verify` section says who performs it. With performer `runner`, the job names the registered **verifier** (a `verifier` service account and the policy revision its report must name), and only a Cannery Row runner holding that account and configured with that revision claims it. With performer `agent`, an `agent` service account or a researcher who did not run the attempt claims it; a claim by the identity that ran the attempt is refused. The verifier **claims** the job with a lease, exactly like an agent claims a unit, receives a job lease token, downloads its inputs through scoped grants (the run's front matter, staged as `claimed.json`, and the run's artifacts; the unit, the brief and the plan come with the claim; the run notes are not an input), uploads outputs under a create-only prefix, and posts its **verification report**. A runner is responsible for safely sandboxing any candidate code it executes; Cannery Row never executes submitted code. Cannery Row still limits the verifier's credentials, input/output access and deadline. Duplicate completion cannot double-publish a result.
4. The verifier checks the claims against the supplied artifacts and writes the verification report: Markdown whose YAML front matter (checked against the published `verification` schema) holds the `pass`, `fail`, or `inconclusive` verdict, a non-empty reason, the policy revision, the result of each gate, the verified measurements, discrepancies, the provenance and, optionally, the comparisons behind the verdict (each value with the reference it was compared against: a paper, a benchmark, a promoted attempt, a baseline), and whose optional body holds its observations. A runner runs the track's producer step and the project's scorer step again, then applies its policy: the stock policy, `cannery evaluator`'s declarative gates from the verifier's versioned configuration, or a project's own policy step. Cannery Row applies no gates itself. It validates the report's metric types/units/slices, completeness, provenance, finite numeric values, artifact manifest and contract version, checks that a `pass` verdict reports every gate as passed and that every comparison cites a verified measurement of the same report, and requires a runner's report to come from the registered verifier under the registered policy revision. Treating missing required evidence as never `pass` is the policy's responsibility (the stock policy reports such a gate `unknown`). The verified measurements and comparisons are indexed, the attempt moves to `verified`, the unit to `documenting`, and a document job opens, whatever the verdict. The verifier cannot make the final decision. Infrastructure failure follows the retry rules above.
5. The unit is written up once, by an agent service account or a researcher who claims its document job ("Write it up" in the web app claims and completes it in one action). The documenter reads the brief, the plan, the unit, every attempt's run document and notes, the failures with their logs, the verification reports and the comments, through the context bundle, and submits the write-up: Markdown whose YAML front matter (the published `writeup` schema) holds a one-sentence `summary`, the `attempts` it covers and the `verification` report it cites by id and SHA-256. A researcher may skip the write-up with a reason, and the decision then shows "No write-up: <reason>"; nothing skips it automatically. The unit then moves to `deciding` and a `decision` review case opens.
6. A researcher sees the write-up, the report, claimed and verified measurements, discrepancies, the verdict and reason, gate results, and source artifacts, then records a decision document: Markdown whose YAML front matter (the published `decision` schema) holds the outcome, `promote`, `reject` or `inconclusive` (`failed` for a unit stopped after a failure), and cites the verification report and the write-up, and whose non-empty body is the reason. Promotion requires a `pass` verdict; a `fail` or `inconclusive` verdict cannot be overridden into promotion without a corrected science revision and a new verification. If the work failed, a researcher instead records `retry` or `stop` on the failure case with a reason. The server attaches the authenticated actor, via, timestamp, and evidence revision. Decisions and reasons are immutable; a correction is a new linked decision event with its own reason.

   The science revision's `decide` section says who decides: `researcher` (the default when it is absent) or `step`, with the registered **decider** (a `decider` service account and the revision of its decider step). With `step`, the decision case opens as before and a **decide job** is queued beside it; only a Cannery Row runner holding that account and configured with that step revision claims it. The decider step reads the decision context bundle (the write-up, the report, the verdict, the brief and the plan) and writes the decision document like a researcher, and the same checks apply: it cites the case's report and write-up, a decider promotes only on a `pass` verdict, and `failed` is only for a unit stopped after a failure. The decision records the decider and its step revision as the actor, and no user. While the decide job waits or runs, a researcher cannot decide the case; once the decision is recorded, a researcher corrects it like any decision, with a new linked decision. A failed or expired decide job runs again up to the science revision's `max_auto_retries`; after that the case is left to researchers. There is no other human override of an automatic decision.
7. The web app shows units, tracks, attempts, events, reports, verified metrics, controls, verdicts and human decisions. It must clearly distinguish agent claims from verified measurements, verifier judgments from human decisions, and pending review from final states. Failures and superseded records remain visible.

The API validates envelope structure; the project's science revision defines scientific meaning. A project's policy can require per-language gates, uncertainty, cost limits, and fresh confirmation. A lower loss alone is not a retrieval win. Passing those gates only makes an attempt eligible for human promotion. Interpreting missing or contradictory evidence as never a pass is the policy's job, as is the choice of gates; Cannery Row checks only that a `pass` verdict reports every gate as passed. Both verifier and human must state their reasoning, including on negative or inconclusive outcomes.

## Verifiers, steps and the runner

Tracks of one project can need different code to exercise a candidate (for example a sparse model versus a dense+sparse hybrid) while their results must stay comparable. A runner verify job is therefore split into container steps run as a chain, followed by the policy:

1. **Producer step, per track.** It runs the candidate and turns it into a project-defined intermediate output, for example ranked results per query. This is the only step that executes candidate code, inside its declared sandbox. It never receives held-out labels.
2. **Scorer step, per project.** It consumes the producer's intermediate output, the ground truth and the frozen claims, and emits the verified measurements, discrepancies and provenance. It never executes candidate code. Because every track uses the same scorer, metrics, slices and uncertainty are computed identically across tracks.
3. **Policy.** The verifier's policy reads the scorer's measurements and gives the verdict: the stock policy's declarative gates, applied in the runner process, or a project's own `policy` step, which has no network, may read held-out labels and baselines, and never reads the attempt's own inputs.

An **interface** is a registered name and version (for example `ranked-run/v1`) with a JSON Schema or format identifier describing the intermediate output. The project's science revision holds the interfaces, the scorer manifest, datasets, controls, metric registry and verifier registration, which together define comparability. Producer manifests are registered separately as immutable, individually revisioned records, so adding a producer for a new track does not mint a new science revision. At claim time the attempt pins the science revision, and the track's producer manifest revision; binding and claim both check that the producer's output interface is the scorer's input interface. A project that prefers a single producer that adapts to the payload binds every track to it.

The **Cannery Row runner** is part of this codebase (`cannery runner`): a separate process that claims verify jobs with a verifier service identity, runs the steps and the policy, moves inputs and outputs between object storage and the containers, verifies checksums, and completes or fails the job. It runs each step through a launcher: a local-process one for fixtures and development, a Docker one (one container per step, see [deployment](deploy.md#the-runner-on-a-container-optimized-os-vm)) and a Kubernetes one (one Pod per step, see [deployment](deploy.md#the-runner-on-kubernetes)). It holds the execution credentials; the API process holds none. Step manifests use the field names of Argo Workflows templates (`container`, `resources`, `activeDeadlineSeconds`, `inputs`/`outputs.artifacts` with `name` and `path`) plus a few Cannery Row extensions, so a later move to Argo Workflows or SkyPilot is a translation, not a redesign. The container contract is defined in [contracts](contracts.md#step-manifests-and-the-container-contract): containers read `/cr/job.json` and `/cr/inputs/<name>/`, write `/cr/outputs/<name>/`, get no network unless declared, hold no credentials and never call the API. A project that does not use the runner sets the verify performer to `agent`: an agent or a researcher who did not run the attempt claims the job and writes the report through the same job API.

The runner has an `experiment` job kind, configured as a `[[kinds]]` entry beside the `verify` kind, for [`workflow` tracks](#experiment-modes). It holds an **experimenter** service token instead of a verifier's, claims units with `{"mode": "workflow"}`, heartbeats the attempt's lease, and runs the workflow's experiment steps in order with the same container contract, launchers, code and setup handling, interface checks and validators as a verify job. An experiment step is candidate code: it never receives held-out labels, and its `code.repo` must be in the science revision's candidate repositories. Its outputs become attempt artifacts (the role is the output's name), its logs `step_log`, `setup_log` and `validator_log`; the last step's `run` output, one `run.md`, becomes the submitted run document. A failure releases the attempt with an error code, the failing step and its logs; the API trusts that report (see the failure classes above).

The runner's `decide` kind, configured with `decider = "<path>"` naming a decider registration (the decider's name, the revision of its step and the step manifest, whose role is `decider`), holds a **decider** service token. It claims decide jobs with `{"phase": "decide", "revision": "<step revision>"}`, heartbeats the job's lease and runs the decider step once with the same container contract and launchers. The step has no network and no input artifacts: it reads the decision context bundle at `/cr/context/context.md`, and writes one `decision.md` to its `decision` output, whose front matter holds the `outcome` and whose body is the reason. The runner sets the document's `verification` and `writeup` to what the job names and completes the job with it; a refused document fails the job with the step's logs.

## Reports, comments and search

Reports are stored in PostgreSQL, not as artifacts: a run's report is its run document, the front matter with its claims and the Markdown body with its run notes, and a verification's report is its front matter with the verdict and the Markdown body with the verifier's observations. Viewers can read reports. Images embedded in a report are uploaded as artifacts with the `report_asset` role, which viewers may read; every other artifact role (raw results, datasets, weights, logs) requires `member` or above. Report size is capped by project configuration.

Members and researchers comment in Markdown on units and attempts. An author can edit their own comment; every edit is retained and visible as history. Comments are discussion, not part of the scientific record: they never change state, verdicts or decisions.

A **general search** covers tracks, units, attempts, verification reports (verdict, reason, observations and discrepancies), decision reasons and comments, within the projects the caller can read, and the reports of claimed result sheets submitted before run documents; run notes are not indexed. It combines full text with facets: project, track, unit state, attempt state, verdict, human decision, actor, and time range. `#123` and `project#123` queries resolve directly. v1 uses PostgreSQL full-text search with the `simple` configuration plus `pg_trgm` trigram matching, which suits mixed French/English text; a dedicated search engine is only warranted by demonstrated need. Results are filtered by permission before ranking, and artifact contents are never indexed. Search is available in the web app, REST and MCP, so an agent can check for prior related work before planning.

## Interfaces

REST is the canonical interface; MCP is a thin, authenticated adapter over the same application methods and permission checks, with no separate persistence or business rules, served over Streamable HTTP by the same process. Initial operations: read and revise the project brief; draft, check, submit and review track plans; list/get/filter/search tracks, units and attempts; manage tracks; claim/heartbeat/release; create scoped upload; record the manifest and submit the run document; claim/heartbeat/complete/fail verify jobs; list events/evidence/metrics/verdicts/review cases; record a human result or failure decision; comment; retrieve a permitted artifact; manage personal access tokens. Human-decision operations require the `researcher` role and a non-empty reason; agent, experimenter, verifier and decider identities cannot call them (a decider records its automatic decisions through its decide job). Status transitions require expected version or lease generation. List APIs paginate and filter by project, track, state, time, metric and dimension; bulk metrics queries serve charts without a query per point.

The dashboard revision defines named views, metric axes/units, slice facets, baseline overlays and default filters, referencing only registered metrics and dimensions, with tracks usable as a grouping dimension. Without dashboard views, the app derives defaults from the metric registry: a table, per-metric timelines and per-dimension breakdowns. Grafana may later consume exported metrics, but is not the primary research UI: reports, provenance, attempt history and decisions need first-class pages.

## Web app design

The audience includes enterprise clients and non-technical viewers, so the app must look calm, modern and trustworthy, while staying compatible with the playful vintage cannery logo. The logo carries the personality; the interface stays plain.

- **Look.** Clean, generous whitespace, one sans-serif typeface (Inter or similar) for everything, no decorative fonts in the UI. Colors come from the logo, used sparingly: deep navy ink for text and navigation, cream as a warm neutral surface, silver-greys for borders and secondary text, and the label's coral red only for the primary action and key highlights. Status colors are semantic and never rely on color alone: every state chip also has a word and an icon. Light theme by default, dark theme supported. Accessible contrast (WCAG AA) and full keyboard navigation.
- **Components.** React with an accessible headless component base (Radix primitives through shadcn/ui, styled with Tailwind), TanStack Query and Table, and one chart library. No custom widget where a standard one exists.
- **Navigation.** One left sidebar with at most six entries, labeled in plain words: **Home** (what needs my attention: plans awaiting review, write-ups to do, decisions to take, failures, running work, and a link to the project brief), **Tracks**, **Units**, **Results** (dashboard views), **Search**, and **Settings** (tokens; project and membership admin only for admins). A project switcher sits at the top of the sidebar and disappears when the user belongs to one project. Search is also a global bar reachable from every page. Actions a role cannot perform are hidden, not disabled.
- **Plain language.** Internal state names never appear raw: `deciding` is shown as "Needs a decision", `agent_claim` as "Reported by agent", `tester_verified` as "Verified". Every unit page answers first, in one sentence at the top, "what was tried, what happened, what was decided and why", before any metrics, evidence or lineage, which stay one click away.
- **Depth on demand.** Lists and pages open on the summary; technical detail (revisions, hashes, manifests, logs, raw envelopes) lives in collapsible sections or a "Details" tab, so a viewer never has to scroll past it and a researcher never loses it.
- **Decisions.** Review flows are one screen: the write-up (or why it was skipped), the evidence summary, the verdict and gate results, the action buttons, and a required reason field. The button stays disabled until a reason is typed, and the confirmation states what will happen in plain words.

## Trust, security and recovery

v1 requires one researcher decision with a reason, not votes or multi-reviewer quorum; retain an append-only decision model so those can be added later. All APIs, pages, reports and artifacts require an authenticated identity with a role on the project; public result pages are outside v1. Treat submitted code, reports, comments and artifact names as untrusted; the web app renders Markdown sanitized. The framework must allowlist object prefixes and media types, cap upload and report sizes, and never pass its DB or broad bucket credentials to a verifier. A runner owns safe execution of candidate code when verification requires it and must declare its sandbox and capability policy; the framework gives it only scoped inputs/outputs and a deadline. A runner verify job's report requires the registered verifier's service identity, and an agent verify job's report requires an identity other than the one that ran the attempt; no one verifies their own run.

PostgreSQL and object storage require backups and restore tests. The DB stores verified object inventory and hashes, but an object is not durable merely because an upload request succeeded. Reconcile orphaned uploads and missing objects; publish an attempt only after verifying required objects. Preserve source/config/verifier identities and all terminal records. Capture cost and duration for queue wait, agent work, verify runtime and total wall time. Use UTC instants in storage and localize only in the UI.

## Generic versus project-specific boundary

Generic: projects, users, roles, tracks, lifecycle, leases, audit, API/MCP, web app, schema registry, object references, upload verification, job queue and failure review, the runner and its container contract, evidence ingestion, metric storage/query, verified comparisons, the stock policy, comments, search, dashboard rendering. Project-specific: unit extension fields, dataset and control identities, interfaces, the scorer step, per-track producer steps and their sandbox, the verifier's policy and its configuration (gates, baseline values), metric registry, required slices, resource budgets, dashboard views. The core may know what a metric, a track and a baseline are; it must not know what nDCG, a GPU, or a particular project's dataset means.
